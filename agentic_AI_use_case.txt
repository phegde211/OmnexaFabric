C) AGENTIC AI - TOOL AND DATA RESOLUTION WITH POLICY-GATED FETCH
===============================================================
This use case applies the same resolution-and-policy mechanism of the main
proposal to an agentic AI mesh. An AI agent must do three things:

    1. FIND   - locate a tool or dataset it is permitted to use.
    2. AUTHORIZE - confirm, per agent, that it may use that destination.
    3. FETCH  - open the approved connection and run the actual call.

These map one-to-one onto the fabric's existing control sequence (Proposal
Section 3): resolve destination and metadata -> obtain policy for the
(source, destination) identity pair -> permit/deny -> establish the approved
path. The agentic case only names the identifiers "tool", "data", "agent" and
places an omnexaAgent/interceptor sidecar beside the agent application, exactly
as the Redis interceptor sits beside the application in Use Case A.

This is EXACT resolution of a REGISTERED key, not search. The agent resolves a
capability identifier that some tool already registered (for example
"tool:web-search"); the fabric returns where it lives. It does not answer "find
me something like a search tool". Registration populates the directory;
resolution looks it up. This is the DNS contract - resolve a name that exists -
generalised from name->IP to UID->destination+metadata.


C.1 Actors
----------
    Agent App      - the agentic application plus its omnexaAgent/interceptor
                     sidecar (the source enforcement point).
    Map server     - identifier -> destination + identity resolution, with the
                     policy authority integrated alongside (Proposal Section 3).
    Tool / Data    - the tool or data endpoint plus its own interceptor; the
                     destination.


C.2 Two separate responsibilities: infra vs. the resolution protocol
--------------------------------------------------------------------
These must not be conflated. The infrastructure does NOT populate the map server
itself; it feeds the metadata to the endpoint's resolution client, which
registers it.

    Infrastructure's duty (Proposal Section 3.1): associate each tool/data
    endpoint with its metadata - identity-tag, capability-UID, attributes - and
    make it available to the endpoint's local resolution client. How the infra
    derives the metadata is out of scope.

    Resolution protocol's duty (Proposal Section 3.2c): the endpoint's resolution
    client - NHRP or LISP, the candidates in the proposal - then REGISTERS that
    metadata with the map server (the NHRP next-hop server or LISP map server),
    via the protocol's registration extension:

        capability-UID (tool type) -> { interceptor IP:port, identity-tag }
        data-key UID   (dataset)   -> { owner interceptor IP:port, identity-tag }

One capability-UID can aggregate many instances - the same summarisation used
for PopID in Use Case A Section 4.3.1 - so one registration can represent a
whole pool of equivalent endpoints, each carrying its own identity-tag. The
identity-tag is what the policy decision keys on later (the TrustSec-style group
of Proposal Section 3.4).


C.3 Sequence
------------

 Agent App                        Map server                      Tool / Data
+ omnexaAgent /               + policy authority                + omnexaAgent /
interceptor                       (alongside)                     interceptor
     |                                 |                               |
  PHASE 0 . registration  (endpoint registers with map server)
     |                                 |  [infra feeds UID + identity] |
     |                                 |<-- register UID + identity ---|
     |                                 |                               |
  PHASE 1 . discover  (exact resolution of a registered key)
     |---- resolve capability-UID ---->|                               |
     |< destination IP + identity (set)|                               |
     |                                 |                               |
  PHASE 2 . authorize  (per-agent, at the source)
     |- get policy (agent-id, tool-id)>|                               |
     |<----------- policy -------------|                               |
     |[enforce at source: DENY -> drop locally]                        |
     |                                 |                               |
  PHASE 3 . connect + fetch  (data plane; bypasses map server)
     |=================== establish approved tunnel ==================>|
     |================ forward actual tool / data call ===============>|
     |<============================ reply =============================|
     |[cache resolve + policy + tunnel; revoke on change]              |
     |                                 |                               |

    Single lines (---) are control-plane exchanges with the map server.
    Double lines (===) are the data plane: a direct tunnel between the agent
    and the destination that does NOT traverse the map server.


C.4 Phase by phase
------------------
PHASE 0 - Registration (infra supplies metadata; resolution client registers).
    The infrastructure feeds each endpoint's resolution client (NHRP or LISP) the
    capability-UID (or data-key UID) and identity-tag. The resolution client then
    registers that mapping with the map server. The infra's job ends at supplying
    the metadata; the registration itself is the resolution protocol's. Nothing
    is discoverable until it has been registered - the precondition of every
    directory, DNS included.

PHASE 1 - Discover (capability #1: UID -> destination resolution).
    The agent's interceptor resolves the capability-UID it needs. The map server
    returns the destination interceptor address, the destination identity-tag,
    and any metadata. If several instances registered under the capability-UID,
    the reply is the SET of them; choosing among them is the agent's decision
    AFTER resolution, not a function of the resolver. A dataset is resolved by
    the identical mechanism - only the UID namespace differs from a tool.

PHASE 2 - Authorize (capability #2: source-side policy on the identity pair).
    Knowing both identities, the interceptor downloads the policy for the
    (agent-identity, tool-identity) pair from the policy authority and enforces
    it AT THE SOURCE. A disallowed (agent, tool) call is dropped locally and
    never leaves the agent host - it is not shipped to a remote gate merely to
    be rejected there. This is the per-agent Zero Trust guarantee: the fabric
    decides whether THIS agent may use THIS tool before a single request is sent.

PHASE 3 - Connect and fetch (capability #3: policy-guided data path).
    On permit, the resolution has already provided underlay reachability, so a
    shortcut path to the destination POP is established over the overlay by the
    chosen protocol's data plane - for example NHRP building a GRE tunnel
    protected by IPsec (strongSwan), or LISP encapsulation. The interceptor then
    forwards the ACTUAL tool or data call through the tunnel; the remote
    interceptor hands it to its local tool/data service as if it had originated
    locally - preserving the call's native semantics, the same way Use Case A
    preserves the RESP request (Section 4.3.2.1 b.3). The reply returns over the
    reverse path. The resolution, the policy and the tunnel are cached while hot
    and valid, and revoked on expiry or change (Proposal Section 3.4).


C.5 Design notes
----------------
    a) Selection is post-resolution, not search. When a capability-UID resolves
       to several endpoints, the agent (optionally steered by policy) selects
       which to use after the exact lookup returns the set. Resolution's
       contract stays "return what is registered under this key".

    b) Registration freshness matters more here than for long-lived POPs - tools
       appear and disappear frequently. The existing expiry/revocation rules
       cover it: a withdrawn tool revokes its mapping and stale entries age out.

    c) Tools, data and peer agents are one mechanism, three namespaces. The same
       resolve -> policy -> connect machinery serves "tool:*", "data:*" and
       "agent:*" identifiers without change.

    d) Policy and transport detail remain design work, as stated throughout the
       proposal. This document explains the architectural fit, not a finished
       specification.
